# 30 — CI do Frontend

## 30.1 Pipeline

```
1. Instalação (npm ci)
2. Geração de tipos do OpenAPI (openapi-typescript contra o openapi.json
   commitado/publicado pelo backend) — falha se o diff resultante não
   estiver já commitado (ver 09-openapi.md §9.4)
3. Lint (ESLint, incluindo eslint-plugin-boundaries — 01-arquitetura.md §1.4 —
   e a regra customizada anti-violet fora de --ai, 13-design-system.md §13.2)
4. Typecheck (tsc --noEmit, strict)
5. Testes unitários (Vitest)
6. Testes de componente (Vitest + Testing Library)
7. Testes de integração (Vitest + MSW)
8. Build (next build)
9. Bundle size (@next/bundle-analyzer — falha se JS inicial > 180 kB gzip)
10. Playwright (E2E, contra MSW — ver 28-mocks.md §28.1)
11. Acessibilidade (@axe-core/playwright, zero violação crítica)
12. Diff de contrato cross-repo (ver §30.4)
13. Scan de dependências (npm audit / equivalente)
14. Scan de secrets (gitleaks ou equivalente)
```

Falha em qualquer etapa bloqueia o merge — mesmo princípio de gate já
aplicado ao backend (`docs/backend/11-testes.md`).

## 30.2 Gate de tipos/mocks desatualizados

A etapa 2 (geração de tipos) e a compilação dos handlers MSW contra esses
tipos (etapa 4, `tsc` já cobre `mocks/` — ver
[28-mocks.md §28.6](28-mocks.md)) são o mecanismo que pega um mock
desatualizado em relação ao contrato **antes** de qualquer teste rodar,
não depois.

## 30.3 Gate de acessibilidade

Etapa 11 — zero violação crítica de `axe-core` bloqueia merge, reafirma
`docs/ux/15-acessibilidade.md` e [24-accessibility.md §24.5](24-accessibility.md).
Violações não-críticas (ex.: contraste em estado hover de um componente
raramente usado) geram aviso, não bloqueio — evita que o gate vire
ruído ignorado.

## 30.4 Diff de contrato cross-repo

O backend já roda `oasdiff` no seu próprio pipeline
(`docs/backend/11-testes.md §11.4`) comparando o OpenAPI da branch contra
a última versão publicada. O frontend roda um job equivalente, na outra
ponta: compara o `openapi.json` da branch atual do **backend** (se
disponível como artefato, ex. workflow disparado por PR no repositório do
backend, ou um artefato publicado) contra o commitado no frontend —
mudança incompatível sem PR correspondente no frontend falha este job
antes de chegar a produção. Este é um gate **novo** desta etapa (não
existia antes, porque não havia frontend para comparar contra).

## 30.5 Orçamento de performance como gate de CI

Reafirma [26-performance.md §26.1](26-performance.md) — `next build`
(etapa 8) mais a análise de bundle (etapa 9) falham se o JS inicial
exceder 180 kB gzip; LCP/INP/CLS são verificados via Lighthouse CI contra
uma build de preview (não contra produção real, que é o papel de
[29-observability.md](29-observability.md)).

## 30.6 O que este pipeline não faz ainda

Reafirma a mesma transparência já usada no backend
(`docs/backend-implementation/18-docker-ci.md`): nenhuma etapa acima foi
**executada** nesta etapa arquitetural — este é o desenho do pipeline
para a implementação (Prompt 6B) configurar, não uma alegação de que ele
já roda.
